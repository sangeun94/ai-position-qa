AI 활용 개발 실무 경험

Q1

Claude Code, Antigravity, Cursor 같은 AI 코딩 도구를 실제 업무에서 어떻게 활용하고 계신가요? 일상적으로 쓰는 워크플로우가 궁금합니다.

주력 도구는 Claude Code입니다. 코드 자동완성 보조가 아니라 개발 파이프라인 자체를 Claude Code 위에 올려서 씁니다. 핵심은 작업 규모에 따라 흐름을 나누는 것입니다. CLAUDE.md에 판단 기준을 규칙으로 정의해 두고 버그 수정이나 필드 추가 같은 작은 작업은 바로 시키는 반면 신규 파일 3개 이상, DB 스키마 변경, 신규 API 2개 이상에 해당하는 작업은 설계 파이프라인으로 진행합니다. AI가 PRD를 작성하면 제가 승인하고 기술 설계서(Spec)를 검증한 뒤 다시 승인하면 테스트 작성, 구현, 검증이 자동으로 진행되는 구조입니다. 승인 게이트를 두 번 두어서 방향 결정은 제가 하고 코드 작성은 AI에 위임합니다.

이 워크플로우를 실제로 만들고 검증한 게 Team Planner입니다. 역할별 커스텀 에이전트 9개(설계·구현·보안감사·계층 간 정합성 검증·시나리오 테스트 등)를 정의하고 /design, /implement 같은 커스텀 스킬로 반복 작업을 명령 하나로 실행하게 했습니다. MCP로는 Playwright를 연동해 구현 결과를 실제 브라우저에서 확인시키고 context7으로 라이브러리 최신 문서를 조회하게 해서 학습 시점 이후 바뀐 API로 인한 오류를 줄입니다. 세션이 끊겨도 planning.md에 작업 상태를 남겨 "이어서"라고만 하면 중단 지점부터 재개되도록 해서 컨텍스트 한계도 관리하고 있습니다. 이 방식으로 1인 개발임에도 일정·칸반·채팅·AI 어시스턴트까지 포함한 협업 플랫폼을 만들 수 있었습니다.

Q2

AI가 생성한 코드를 어느 정도까지 신뢰하고, 어떤 기준으로 검증/리뷰하시나요?

AI 코드는 초안으로 보고 신뢰는 코드 자체가 아니라 검증 절차에 둡니다. 일정 규모 이상 작업은 스펙과 테스트를 먼저 만든 뒤 구현하게 해서 코드의 정오를 테스트가 판정하게 합니다. 그 위에 검증 전담 에이전트를 직접 만들어 두었는데 빌드가 통과하면 보안 감사(인증·입력 검증·민감 정보), 계층 간 정합성 검증(Spring↔Express 간 API 경로·환경변수 불일치), 시나리오 테스트(멱등성·경계값·부분 실패)를 병렬로 돌리고 전부 통과해야 완료로 선언됩니다. UI는 Playwright를 연동해 AI가 말로 보고하는 게 아니라 실제 브라우저 동작을 확인한 결과를 가져오게 하고 존재하지 않는 API를 지어내는 문제는 context7으로 최신 공식 문서를 조회하며 짜게 해서 줄입니다.

사람 확인은 두 지점에서 합니다. AI가 코드를 수정할 때 변경분(diff)을 그대로 통과시키지 않고 의도한 파일 외에 다른 곳을 건드리지 않았는지, 기존 구조와 어긋나지 않는지 확인한 뒤 반영합니다. 그리고 Team Planner는 1인 개발이라 문제가 전부 저에게 돌아오는 구조였기 때문에 기능 단위로 직접 실행해 보며 확인하는 습관이 생겼습니다. 경험상 AI 코드는 문법보다 컨텍스트에서 틀립니다. 코드만 보면 그럴듯한데 기존 코드베이스 규칙과 어긋나거나 엣지 케이스를 빼먹는 식이라 리뷰할 때도 "돌아가는가"보다 "기존 구조와 맞는가, 빠진 경우가 없는가"를 먼저 봅니다.

Q3

여러 AI 에이전트를 조합해 작업을 자동화하거나, 커스텀 훅/스킬/워크플로우를 직접 만들어 보신 경험이 있으신가요?

Team Planner를 개발하면서 Claude Code 위에 멀티 에이전트 파이프라인을 직접 만들어 썼습니다. 역할별 커스텀 에이전트 9개를 정의했는데 요구사항을 분석해 작업 규모를 판단하는 Orchestrator, PRD와 Spec을 작성하는 Architect, 테스트를 먼저 쓰고 구현하는 Developer, 검증 전담인 SecurityAuditor·CrossLayerVerifier·ScenarioTester 등입니다. 빌드가 통과하면 보안 감사, 계층 간 정합성 검증, 품질 검증 세 에이전트를 병렬로 실행하고 전부 통과해야 완료로 선언되는 11단계 워크플로우이고 실패 시 재시도 횟수와 사용자 에스컬레이션 조건까지 규칙으로 정의했습니다. 이 중 CrossLayerVerifier는 실제 반복해서 겪던 문제에서 나왔습니다. Spring과 Express 두 백엔드를 쓰는 구조라 API 경로나 환경변수가 계층 간에 어긋나는 버그가 잦았는데 그 체크리스트를 에이전트 정의로 만들어 매번 자동으로 검증하게 했습니다.

반복 작업은 커스텀 스킬(슬래시 명령)로 만들었습니다. /design은 요구사항을 받아 PRD부터 추적 문서까지 생성하고 /implement는 설계 문서를 읽어 테스트 작성부터 구현까지 단계별로 진행하며 중단 지점부터 재개하는 옵션도 있습니다. 커밋과 배포도 스킬로 만들었는데 /commit은 변경사항을 기능 단위로 분리해 커밋 규칙에 맞춰 GitHub과 GitLab 양쪽에 푸시하고 "배포"라고 덧붙이면 main 머지까지 진행합니다. /deploy는 마지막 배포 이후 바뀐 파일을 분석해 프론트엔드·Spring·Express 중 변경된 서비스만 골라 Docker 빌드 후 서버에 배포합니다. 개발 도구만이 아니라 제품 안에서도 에이전트를 조합해 봤습니다. Team Planner의 채팅에는 설정이 다른 봇 여러 개가 같은 채널에 공존하는데 봇마다 전용 계정과 프롬프트, 사용할 수 있는 툴 허용 목록을 분리했고 봇끼리 자동 대화하는 기능에서는 한 봇이 혼자 채널을 도배하지 않도록 연속 메시지 수를 제한하는 규칙을 두었습니다. 훅은 아직 사용해 본 적이 없지만 에이전트와 스킬, 워크플로우는 만들어 본 수준을 넘어 지금도 매일 개발 사이클에서 쓰고 있습니다.

Q4

Team Planner 프로젝트에 AI 어시스턴트를 직접 통합하신 것으로 알고 있는데, 어떤 방식(API 연동/에이전트 설계 등)으로 구현하셨는지 궁금합니다.

세 층으로 나눠 구현했습니다. 먼저 아키텍처 층에서 AI 전담 Express 서버를 Spring 메인 API와 분리했습니다. Express는 DB에 직접 접근하지 않고 모든 데이터를 Spring 내부 API 경유로 가져오게 해서 AI 기능이 권한 체계를 우회할 수 없게 했습니다. LLM은 Vercel AI SDK로 OpenAI와 Anthropic을 추상화해 관리자 설정으로 모델을 전환할 수 있고 API 키는 Spring이 암호화 보관합니다.

에이전트 층은 툴 콜링 루프로 설계했습니다. 보고서·일정·칸반·연차 등 도메인 툴 약 75개를 정의해 LLM이 "판단→툴 호출→결과 확인"을 반복하며 실제 업무 데이터를 조작하게 했고 모든 툴이 Spring REST를 호출하므로 권한 검증은 서버에서 이뤄집니다. 채팅에서는 @멘션으로 봇을 호출하는데 봇마다 전용 JWT와 프롬프트(역할·제약·가드레일 5계층, DB 관리)를 갖고 rate limit(호출 횟수 제한)과 툴 화이트리스트(허용 목록)로 제어됩니다. MCP는 양방향으로 구현했습니다. 외부 MCP 서버의 툴을 연결해 내장 툴과 합쳐 쓰는 클라이언트와 Team Planner의 툴을 외부에 노출하는 MCP 서버를 모두 만들었습니다.

지식 층은 RAG입니다. 보고서·일정·칸반 데이터가 저장되면 커밋 후 비동기로 임베딩을 생성해 PostgreSQL pgvector에 저장하고(HNSW 인덱스) 콘텐츠 해시를 비교해 변경이 없으면 임베딩 API 호출을 건너뛰는 증분 갱신(바뀐 것만 갱신)을 넣었습니다. 검색은 본인 데이터와 소속 프로젝트로 권한을 스코핑했고 업로드 문서는 마크다운 구조 기준으로 청킹해 임베딩하며 벡터 검색 결과가 없으면 키워드 검색으로 폴백합니다. 이렇게 조회된 컨텍스트를 시스템 프롬프트에 주입해 "맥락에 없는 내용은 추측하지 말라"는 제약과 함께 응답을 생성합니다.

Q5

한기대 AI 챗봇 연구 과제에서 다루신 LLM·NLU 관련 경험이, 실제 서비스 개발에 AI를 접목하는 데 어떻게 도움이 되셨나요?

연구와 구현이 시기적으로 맞물리면서 연구에서 설계한 것을 곧바로 실제 서비스에서 검증할 수 있었습니다. 연구에서는 지식을 넣는 방식으로 Fine-tuning과 RAG를 비용·정확도·운영 관점에서 비교했고 이 덕분에 Team Planner의 AI 어시스턴트를 만들 때 "기관 문서 기반 응답에는 문서만 갱신하면 되는 RAG가 현실적"이라는 판단을 근거를 갖고 내릴 수 있었습니다. 지식베이스 설계도 마찬가지입니다. 연구에서 문서 정제부터 청킹, 임베딩, 벡터 DB 적재까지의 파이프라인과 해시 기반 변경 감지로 불필요한 재임베딩을 막는 구조를 설계했고 Team Planner에서 그 구조를 그대로 구현했습니다.

응답을 통제하는 체계도 연구에서 가져왔습니다. 연구에서 LLM 응답을 통제하는 수단으로 Prompt Conditioning을 다뤘는데 역할·정책·컨텍스트·안전·출력 형식의 5단계 프롬프트 구조로 설계했고 Team Planner의 봇 프롬프트를 같은 5계층으로 나눠 DB에서 관리하도록 구현했습니다. 근거 없는 응답을 차단하는 정책이나 대량 호출을 막는 호출 제한도 연구에서 정리한 운영 기준을 실제 코드로 옮긴 것입니다. 반대 방향의 도움도 있었습니다. 직접 구현하고 운영해 본 경험이 있으니 연구 보고서가 이론 정리에 그치지 않고 실제 도입 시 비용과 리스크를 현실적으로 짚는 결과물이 될 수 있었습니다.

— Section 02

문제 해결 및 협업 방식

Q6

AI가 잘못된 결과를 낼 때, 원인을 어떻게 추적하고 대응하시나요?

경험상 AI가 틀리는 원인은 대부분 모델이 아니라 컨텍스트에 있습니다. 참조할 규칙이 없거나 설계 문서가 모호한 경우라서 이상한 결과가 나오면 AI가 무엇을 근거로 판단했는지부터 확인합니다. 대응은 그 자리의 채팅으로 바로잡는 데서 끝내지 않고 원인이 된 문서를 고칩니다. 규칙이 없어서 틀렸으면 CLAUDE.md에 추가하고 설계가 모호했으면 설계 문서를 수정합니다. 같은 실수가 반복되면 아예 검증을 자동화하는데 Spring과 Express 간 API 경로가 어긋나는 실수가 잦아서 그 체크리스트를 검증 에이전트로 만든 게 그 예입니다. 서비스 봇에는 감사 로그 개념으로 툴 호출 기록을 전부 DB에 남겨서 틀린 답이 나오면 데이터 조회가 틀렸는지, 답변 생성이 틀렸는지, 조회 없이 지어냈는지 구분해 원인을 추적했습니다.

Q7

프롬프트/컨텍스트 관리에서 본인만의 노하우나 원칙이 있다면 말씀해 주실 수 있을까요?

원칙은 두 가지입니다. 첫째, 컨텍스트를 대화가 아니라 파일로 관리합니다. 채팅으로 준 지시는 세션이 끝나면 사라지지만 파일은 누적되기 때문에 규칙은 CLAUDE.md와 규칙 파일에, 기능 설계는 설계 문서에, 진행 상태는 planning.md에 남겨서 어떤 세션에서든 같은 컨텍스트로 시작하게 합니다. 둘째, 컨텍스트를 얇게 유지합니다. 다 넣어주면 잘할 것 같지만 실제로는 핵심 규칙이 묻혀서 오히려 품질이 떨어지기 때문에 CLAUDE.md는 목차만 있는 인덱스로 유지하고 상세 내용은 주제별 문서로 분리해서 필요한 것만 읽게 합니다. 그리고 이 규칙들을 고정해 두지 않고 계속 고칩니다. AI와 작업하다 반복되는 실수를 발견하면 그때그때 규칙에 반영하고 동료들과 얘기하다 좋은 방식을 들으면 가져와 적용하고 에이전틱 엔지니어링 사례도 찾아보면서 워크플로우 자체를 개선 대상으로 다루고 있습니다.

Q8

사람이 하던 리뷰·설계 역할과 AI 활용 사이에서, 어디까지를 AI에 맡기고 어디부터는 직접 하시는 편인가요?

기준은 "만드는 일은 AI에, 결정하는 일은 사람에"입니다. 설계에서 AI는 PRD와 기술 설계서 초안을 작성하고 기존 코드베이스와의 정합성도 검토하지만 무엇을 만들지, 어떤 아키텍처로 갈지, 설계를 승인할지는 제가 결정합니다. 실제로 워크플로우에 승인 게이트를 두 번 두어서 문서 단계에서 방향을 제가 확정한 뒤에만 구현이 진행되게 했습니다. 리뷰도 같은 구조입니다. 테스트 통과나 보안 점검, 계층 간 정합성 같은 1차 검증은 자동화와 AI에 맡기고 저는 그 결과 위에서 최종 판단을 합니다. 특히 DB 스키마나 아키텍처처럼 되돌리기 어려운 결정과 변경분이 기존 구조와 맞는지에 대한 판단은 반드시 직접 합니다. 이렇게 나누는 이유는 AI가 틀릴 때도 그럴듯하게 틀리기 때문입니다. 읽고 판단할 수 있는 사람이 결정권을 쥐고 있어야 AI를 안전하게 쓸 수 있고 결과에 대한 책임도 AI가 아니라 제가 지는 것이라고 생각합니다.

포지션 적합성 및 동기

Q9

Team Planner처럼 기획부터 배포까지 혼자 책임지고 진행하신 경험이 있으신데, AI 하네스를 활용한 개발도 이와 비슷하게 스스로 판단하고 주도하는 성격의 업무입니다. 이런 방식의 업무가 본인과 잘 맞는다고 느끼시나요?

잘 맞는다고 생각합니다. Team Planner는 누가 시켜서 시작한 게 아니라 주간 보고를 하다가 "개발 회사인데 보고 도구를 직접 만들면 되지 않나"라는 의문이 들어 혼자 만들기 시작한 프로젝트였습니다. 결과물이 대표님 눈에 들면서 회사 메인 프로젝트가 됐고 이후 일정·칸반·채팅·AI 어시스턴트까지 무엇을 언제 어떤 구조로 만들지 전부 스스로 판단하며 확장했습니다. AI를 활용하는 개발 방식 자체도 같은 과정으로 만들었습니다. 정해진 방법론이 있어서 따른 게 아니라 어떻게 하면 AI와 더 잘 일할 수 있을지 스스로 찾아가며 에이전트와 워크플로우를 직접 설계했고 지금도 계속 고치고 있습니다. 다만 혼자 판단한다는 것이 독단적으로 한다는 뜻은 아니라고 생각합니다. 판단의 근거를 설계 문서로 남기고 중요한 갈림길에서는 확인을 거치는 습관을 들였는데 혼자 일할수록 판단을 검증할 장치가 필요하다고 느꼈기 때문입니다. 스스로 방향을 정하되 그 판단을 기록하고 검증받을 수 있게 일하는 방식이 저에게 가장 잘 맞습니다.

Q10

AI 활용 개발 포지션으로 전환하는 것에 대해 어떤 기대나 우려가 있으신가요?

기대가 더 큽니다. 지금까지는 AI 활용 워크플로우를 혼자 만들고 혼자 검증해 왔는데 이 포지션에서는 그게 개인 실험이 아니라 본업이 되고 같은 고민을 하는 동료들과 방식을 비교하며 다듬을 수 있다는 점이 가장 기대됩니다. 우려는 두 가지가 있는데 사실 첫 번째 우려가 이 기대와 연결됩니다. 혼자 AI와 일하다 보면 지금 방식이 맞는 방향인지 스스로 검증하기 어렵다는 점입니다. 제 나름의 워크플로우를 만들긴 했지만 이게 좋은 방법인지 비교할 대상이 없었고 그래서 팀 안에서 리뷰와 피드백을 받으며 일하는 환경을 오히려 필요로 하고 있습니다. 두 번째는 코드 이해에 대한 우려입니다. 손으로 한 줄씩 짤 때는 코드 흐름이 자연스럽게 몸에 남는데 AI 활용 개발은 무게가 "코드를 어떻게 쓰나"에서 "AI를 어떻게 현명하게 굴리나"로 옮겨가다 보니 코드에 대한 깊이가 옅어질 수 있다고 생각합니다. 그래서 인증이나 권한, 핵심 도메인 로직처럼 파급이 큰 부분은 AI가 짰더라도 반드시 직접 읽고 이해하고 넘어가는 습관을 유지하려고 합니다. 읽고 판단하는 능력이 무너지면 AI 활용 자체가 무너진다고 보기 때문입니다.

Q11

이 방향으로 커리어를 발전시키고 싶으시다면 이유가 궁금합니다.

지난 2년 동안 제안서 작성과 PM·PMO, 개발, 운영 유지보수까지 한 사이클을 폭넓게 경험했습니다. 덕분에 시스템이 만들어지고 운영되는 전체 흐름을 이해하게 됐지만 한 분야를 전문적으로 파고들 기회가 없었다는 아쉬움도 남았습니다. 그래서 다음 단계는 개발로 다시 무게를 옮겨 깊이 있게 성과로 기여하는 것이라고 정했고 그 깊이의 방향이 AI 활용 개발이라고 생각합니다. 이유는 두 가지입니다. 하나는 이미 스스로 파고들고 있던 영역이기 때문입니다. Team Planner에서 AI 어시스턴트를 직접 구현하고 개발 워크플로우에 에이전트를 붙여가며 일해 왔는데 이걸 취미 수준이 아니라 전문성으로 만들고 싶습니다. 다른 하나는 폭넓게 쌓은 경험이 이 분야에서는 그대로 강점이 되기 때문입니다. AI에게 일을 맡기는 과정은 결국 요구사항을 정의하고 산출물을 검증하고 운영 기준을 세우는 일인데 기획과 사업관리, 운영을 거치며 해온 일들이 정확히 그것이었습니다. 흩어져 있던 경험이 하나로 모이는 자리가 AI 활용 개발이라고 느꼈고 그래서 이 방향으로 커리어를 쌓고 싶습니다.
